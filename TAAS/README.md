# KoROAD 세부링크 도로위험지수 API — 연결 테스트 기록 (2026-08-24)

DSI 파이프라인 산출물을 외부 지수로 교차검증할 수 있는지 확인하기 위한 사전 테스트.

## 결론

**강릉시 시내 도로 · 차종=버스(02) 로 실제 값이 정상 수신된다.** 다만 아래 3가지 제약 때문에
DSI 검증용으로 쓰려면 설계를 조정해야 한다.

1. 커버리지가 낮다 (도로에 따라 5~98%). 세부링크 망에 없는 구간은 값을 받을 수 없다.
2. **실시간(5분 주기) 지수**다. DSI 는 촬영일 교통과 무관한 구조적 지표이므로 성질이 다르다.
3. 일일 호출 허용량이 작다. 하루치를 다 태우면 `resultCode=30` 으로 키가 차단된다.

## API 사양 (실측 확인)

```
GET https://opendata.koroad.or.kr/data/rest/road/dgdgr/link
  authKey          발급 인증키
  searchLineString LineString(lon lat,lon lat,...)   EPSG:4326
  vhctyCd          01 승용차 / 02 버스 / 03 택시 / 04 화물차
  type             json | xml
  numOfRows, pageNo
```

응답은 **입력 폴리라인의 세그먼트마다** 1건:
`index`, `line_string`(입력 좌표 그대로 에코), `anals_value`(위험지수), `anals_grd`(위험등급).

### resultCode

| code | 의미 | 대응 |
|:--|:--|:--|
| `00` | 정상 | — |
| `03` | 해당 데이터 없음 | 결측 처리 |
| `10` | 파라미터 오류 **또는 세부링크 미매칭** | 이분 분할로 살릴 세그먼트 분리 |
| `30` | `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` (허용량 소진/키 차단) | **즉시 실행 중단** |

### 함정 — `10` 의 정체

문서에 없는 동작. **입력 세그먼트 중 하나라도 내부 세부링크에 매칭되지 않으면 요청 전체가 `10`** 이 된다.
`03`(NODATA) 이 아니라 파라미터 오류로 떨어지므로, 다중 세그먼트 요청은 실패 시 이분 분할해서
매칭 가능한 세그먼트만 건져야 한다.

실측 예 (강릉대로, 50m 간격 단독 조회):

```
seg[0]   0~ 50m  code=00 val=5.53  grd=2
seg[1]  50~100m  code=00 val=0.00  grd=1
seg[2] 100~150m  code=10  <- 이 구간이 섞이면 그 요청 전체가 실패
seg[3] 150~200m  code=00 val=0.22  grd=1
```

이 때문에 처음엔 "정점 6개 제한"으로 오독했다. 정점 수 제한이 아니고, 실패 세그먼트의 포함 여부다.
(2점 500m 요청도 정상 동작한다.)

### 그 밖에 확인한 것

- 인접 세그먼트가 같은 세부링크에 물리면 동일 값이 반복된다 (세부링크 단위: 교차로 30m / 일반도로 100m).
  따라서 50m 보다 촘촘히 샘플링해도 정보량은 늘지 않고 호출 수만 늘어난다.
- 좌표 소수점 자리수(4~13자리)는 결과에 영향 없음.
- 강릉대로 특정 구간에서 `vhctyCd` 01/02/03/04 가 모두 같은 값(79.33)이었다.
  문서 샘플(서울)에서는 01=0.88 / 02=0.90 으로 달랐다. **차종 반영 여부는 추가 확인 필요.**

## 허용량 소진 경위와 재발 방지

병렬 프로빙(workers=6~8)으로 하루에 2,200회 이상 호출해 키가 차단됐다.
차단 직후에는 API 경로가 `connect timeout` 으로 응답조차 하지 않다가, 이후 `resultCode=30` 으로 바뀐다.

초기 `koroad_client.py` 는 `code != "00"` 을 전부 "세부링크 미매칭"으로 처리했기 때문에
**차단·네트워크 실패가 결측으로 위장되어 매칭률 통계가 오염**됐다.
(간격 민감도 테스트에서 노선 A 가 대부분 0% 로 나온 것이 이 오염의 결과다. 위 표의 도로단위
수집분도 일부 오염 가능성이 남아 있어, 재수집으로 재확인해야 한다.)

현재 `koroad_client.py` 는 이를 구분한다.
- `30` / 네트워크 실패 → `QuotaError` 로 즉시 중단
- `Client(budget=N)` 으로 실행당 호출 상한
- `cli.codes` 에 resultCode 분포 기록
- 러너의 `save()` 는 빈/부분 결과가 기존 파일을 덮어쓰지 않게 막음

노선 A/B/C 전체(415 세그먼트) ≈ 1,000회. 하루 예산을 보고 `budget` 을 정할 것.

## DSI 검증용으로 쓸 때 남은 쟁점

- **성질 불일치.** 본 지수는 실시간(5분) 값이고 DSI 는 구조적 지표다. 시점 편차를 줄이려면
  같은 구간을 여러 시각에 반복 수집해 평균/분산을 봐야 하는데, 그러면 호출 수가 배로 든다.
- **커버리지.** 미매칭 구간이 절반 가까이라 노선 전체 비교가 아니라 매칭된 구간만의 부분 비교가 된다.
  구도심 이면도로에서 특히 비어 있는데, DSI 가 높게 나오는 곳도 주로 이런 구간이라 하필 겹친다.
- **정적 대안은 검토 후 제외.** 링크기반 사고위험지역(`/data/rest/accident/riskArea`, CSV 일괄 제공)과
  지자체별 교통사고 다발지역을 받아 봤다. 성질은 DSI 에 더 맞았지만 사고 이력 기반이라
  "사고 난 적 없는 구간도 사전 진단한다"는 DSI 의 취지와는 결이 달랐다.
  본 지수를 쓰기로 하고 해당 자료는 정리했다.

## 이 폴더에 남긴 것 (2026-08-31 정리)

세부링크 도로위험지수는 **실시간(5분 주기) 지표라 CSV 일괄 제공이 없고 API 호출로만** 받을 수 있다.
그래서 이 API 관련 파일만 남기고 나머지는 삭제했다.

| 파일 | 역할 |
|:--|:--|
| `.env` | `DANGER_INDEX_API_KEY` |
| `koroad_client.py` | API 클라이언트 (resultCode 구분 · 이분분할 · 호출 예산 · `QuotaError`) |
| `run_bus_routes.py` | 셔틀 후보노선 A/B/C 수집 |
| `run_gangneung_bus.py` | 주요 시내 도로 수집 |
| `gangneung_bus_dgdgr.json` | 주요 시내 도로 수집분 (2026-08-24, 172/302 세그먼트) |

`bus_routes_dgdgr.json` 은 내용이 `{}` 인 빈 파일이라 함께 지웠다.
(수집분을 빈 결과로 덮어썼던 흔적이고, `run_bus_routes.py` 를 다시 돌리면 새로 생성된다.)
